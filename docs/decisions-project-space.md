# 决策记录 · 项目空间（decisions-project-space）

> 规则：每个结论写「结论 + 理由」；未定项单列；改了旧结论不删，追加「取代」关系。
> 来源：2026-11-03 群主要求 + grill 追问。

## 已定

### DP-1 存储放服务端，不放本机文件
- 结论：项目与记忆落 `ds-teams` 服务端（`data/projects/`），API 读写。
- 理由：多端同步必须有一个真源；本机文件在 QQ 端/桌面端/网页之间无法天然共享，回到「各自记各自的」。群主 2026-11-03 11:14 明确「建议服务端」。

### DP-2 能力工具化，不靠提示词承载
- 结论：项目上下文只能通过 `project_open / memory_recall / memory_save / project_rules / project_state` 这组工具读写；系统提示只留「开工先调 project_open」一句。
- 理由：群主原话「像 bcdp 的浏览器操作一样」，关键能力必须是常驻、可调用、有存储的工具；提示词里的内容会随会话丢失，也无法验证是否生效。

### DP-3 索引与正文分离
- 结论：`project_open` 返回 2KB 级索引（规则/未决/最近决定/活跃任务/游标），细节走 `memory_recall`。
- 理由：新会话冷启动要快；全量正文塞进首轮会再次变成「上下文里的一坨」，和要解决的问题同构。

### DP-4 记忆 append-only，修正用取代链
- 结论：写入只追加，改错用 `supersede` 指回旧条；索引从 active 条目重算。
- 理由：协作场景里「谁在什么时候改了什么」比「当前长什么样」更需要可回溯；也避免并发写覆盖。

### DP-5 账号绑定与端解耦
- 结论：记忆按 `accountId` 共享，`end`（qq/web/desktop）只作为审计字段。
- 理由：群主的需求是「同一账号同一项目空间多端同步」；把端当权限边界会让换端变成换身份。

### DP-6 先落 M1–M3 最小闭环，历史房间不迁移
- 结论：今天只做设计稿 + 审计；随后 M1 存储/API、M2 工具、M3 冷启动演练；61 个归档房间不动。
- 理由：群主说「今天先调整未来新会话的影响」；历史房间是验证素材，不是待迁移数据。

### DP-7 任务状态单真源：台账为主，项目空间只读镜像
- 结论：`data/dispatch-state.json`（dispatch 台账）是任务状态唯一真源；项目空间的 `activeTasks` 只做读时派生，`POST /memory` 的 `kind=task` 一律 403；项目 `roomIds` 决定从台账取哪些房间。
- 理由：两天里已发生「台账 vs progress.md vs 房间任务卡」三处各写一次的口径漂移；M2 之后若再允许写 task 记忆，必然出现两套任务状态。巡检已用台账判「是否收口」（server.mjs:548-581），沿用同一真源。
